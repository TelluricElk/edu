# EduAppML — заметки для разработки (свои и AI-ассистента)

## Расположение файла

Кладётся в **корень репозитория**, рядом с `build.gradle`, `settings.gradle`,
`gradlew` (не внутри `app/`).

На вашей текущей машине (судя по пути из лога ошибки сборки) это:
```
C:\Users\sasaa\yurovskiy\kozlov\EduAppML v.19\DEVELOPMENT_NOTES.md
```

Переносимо (если проект переедет в другую папку или на другую машину) —
ориентир такой: файл должен лежать **на одном уровне** с `settings.gradle`,
то есть там же, где корень Gradle-проекта, а не внутри модуля `app`.

Этот документ — накопленный опыт по ходу наполнения всех 19 тем приложения
(9 классических алгоритмов + 10 нейросетевых архитектур). Все пункты ниже —
реальные ошибки, которые где-то в процессе реально всплывали и были
исправлены. Цель документа — чтобы при добавлении новых тем (а всегда можно
добавить VAE, Vision Transformer, Mixture of Experts и так далее) эти же
грабли не приходилось находить заново.

## 1. Структура контента одной темы

Каждая тема — это 6 спутниковых экранов вокруг центрального пузыря
(`NodeDetailScreen.kt`, порядок по часовой стрелке): **Теория → Задача →
Мат. основа → Код → Интерактив → Решение**.

### `general.ru.md` (Теория) — ровно 9 разделов `###`

1. Сцена — конкретный пример/метафора, **привязанная к тому же датасету**,
   что используется в интерактиве этой темы. Не абстрактное описание,
   а история с местом действия.
2. Немного истории — реальные имена, реальные годы.
3. Где это применяется — 4-5 пунктов.
4. Как это работает — подраздел "На пальцах" (без формул) + подраздел
   "Чуть более технически" (с понятиями, но без формул — формулы в
   Мат. основе).
5. Терминология — 4-6 терминов.
6. Философия метода — и его цена — что метод даёт и чем расплачивается.
7. Резюме — короткий абзац + явный переход "переходите к «Эталонной
   задаче», а затем в «Интерактив»".

Все 19 файлов на момент написания этого документа выдержаны в этой
структуре (`grep -c "^###"` даёт 9 везде). Если добьётесь другого числа —
скорее всего, что-то забыто или лишнее.

### `task.ru.md` (Задача)

Конкретный сценарий → "Что нужно сделать" → "Ваша цель в интерактиве"
(нумерованный список, 2-4 пункта) → "Зачем это нужно" → указание перейти
к "Решению задачи".

### `math.ru.md` (Мат. основа) — см. раздел 3 про LaTeX

### `impl.ru.md` (Код)

Python-реализация "с нуля" → "Готовое решение" (аналог на sklearn/PyTorch/
etc.) → "А что реально считает интерактив в этом приложении" (Kotlin-
фрагмент, СООТВЕТСТВУЮЩИЙ реальному коду в `*Lab.kt`, а не выдуманный) →
"Важная оговорка" (что упрощено и почему).

### `*Result.kt` (Решение)

Карточка "Эталонное решение" (конкретные параметры + посчитанный на лету
результат — НЕ хардкодить ожидаемое число, если оно зависит от расчёта,
считать через `remember { Lab.train(...) }`) → карточка "Полученные
знания" (4 пункта bullet list) → `QuizSection` с **ровно 4 вопросами**
(`QuizQuestion`/`QuizOption` из `ui.common`).

### `*Interactive.kt` (Интерактив)

`LessonScaffold` с параметрами `eyebrow`/`title`/`onBack`/`onNext`. Слайдеры
завязаны на параметры `Lab.train(...)`. **У каждого интерактива должно быть
живое текстовое пояснение**, которое меняется вместе с тем, что реально
меняет пользователь — даже если это не гиперпараметр обучения, а, например,
точка на графике (NB) или выбранное слово (Transformer). Проверить:
`grep -c "insight" *Interactive.kt` — если 0, скорее всего, забыли добавить.

## 2. Compose: технические грабли

### 2.1. `clickable` вместо `pointerInput + detectTapGestures` для простых тапов

**Проблема:** `LessonScaffold` оборачивает контент в `verticalScroll`.
Дискретные кнопки-переключатели (сегменты "метрика A / метрика B" и т.п.),
реализованные через `.pointerInput(key) { detectTapGestures { ... } }`,
иногда "съедают" первые тапы — родительский скролл-контейнер может
перехватить жест раньше, чем вложенный `detectTapGestures` успевает
засчитать его как тап. Проявлялось не всегда и не для всех кнопок сразу
(в одном случае — только для двух из шести кнопок в `NodeDetailScreen`,
но там причина была другая, см. 2.3).

**Правило:** для простого тапа по дискретному элементу (кнопка, переключатель,
сегмент) — всегда `Modifier.clickable { onAction() }`. `detectTapGestures`
оставлять **только** там, где реально нужны координаты тапа (тап по графику
для указания точки, рисование на холсте). `Modifier.clickable` не даёт
координат — если они нужны, альтернативы `detectTapGestures` нет.

**Мини-таргет:** держать кликабельные элементы не меньше **44dp** (Android
рекомендует 48dp).

### 2.2. `Array<FloatArray>` — ловушка с `.flatten()` и цепочками `.maxOf{}`

`Array<FloatArray>.flatten()` **не существует** в Kotlin stdlib (`flatten()`
определён для `Array<Array<T>>`, а `FloatArray` — не `Array<Float>`, это
отдельный примитивный тип). Ошибка компиляции при этом выглядит очень не
похоже на реальную причину: "Cannot infer type for this parameter",
"Unresolved reference 'it'", "Overload resolution ambiguity" — все три сразу,
хотя причина одна: `.flatten()` не найден, и всё, что дальше в цепочке
(`.maxOf { abs(it) }`), не может вывести типы.

**Правило:** для `Array<FloatArray>` — только явные циклы:
```kotlin
var maxV = 0.01f
for (row in arr) {
    for (v in row) {
        if (v > maxV) maxV = v
    }
}
```
Обычные `.maxOf{}` на `IntRange`/`List<T>`/`FloatArray` (без предварительного
`.flatten()`) — безопасны, это другой случай.

### 2.3. Не связанные с математикой визуальные пропадания линий/элементов

Если что-то не отрисовывается для конкретного угла/позиции (например, ровно
вертикальная или горизонтальная линия на Canvas), а расчёт координат при
проверке оказывается математически верным (не NaN, не деление на ноль) —
подозревать:
- Неприменимые path-эффекты (`PathEffect.cornerPathEffect` на простой
  двухточечной линии — скруглять там нечего, эффект лишний).
- Слишком тонкую/бледную линию на грани субпиксельного антиалиасинга
  (`strokeWidth` меньше 3-4px при alpha < 0.3 — рискованно для строго
  осевых линий). Увеличение толщины и alpha — безопасный фикс независимо
  от точной причины.

### 2.4. Экранирование кавычек в Kotlin-строках

Русский текст часто просит кавычки для выделения слова. Обычные `"..."`
внутри строки, ограниченной `"..."`, **обрывают строку** без предупреждения
компилятора о реальной причине (ошибка будет про что-то дальше в файле).

**Правило:** для выделения слова внутри Kotlin-строки — всегда «ёлочки»,
никогда прямые кавычки:
```kotlin
"Хорошо: «застрявших» между шагами."      // OK
"Плохо: "застрявших" между шагами."       // ломает строку
```

## 3. LaTeX (Markwon + JLatexMathPlugin) — правила формул

Полная история этой боли — в самом начале проекта (тема kNN), заново
проверять не нужно, но правила таковы:

1. **Только блочный формат**, `$$` на **отдельной строке**, с пустыми
   строками до и после (отдельный абзац):
   ```
   $$
   d(x, x_i) = \sqrt{(x-x_i)^2}
   $$
   ```
   Однострочный `$$formula$$` и одиночный `$x$` внутри предложения —
   не используются вообще. Переменные в прозе — просто текст или `*курсив*`.
2. **Никакой кириллицы внутри `$...$`/`$$...$$`**, включая внутри `\text{}`.
   Даже одно русское слово в `\text{}` ломает рендер всей формулы.
   Пояснение переносится в обычный текст до/после формулы.
3. **Никакого `\mathbb{}`.** Библиотека, судя по всему, не тянет нужный
   шрифтовый пакет. `\mathbb{R}` → `\mathbf{R}`. `\mathbb{E}` → просто `E`
   (обычная буква, без обёртки). `\mathbb{1}(...)` (скобка Айверсона) →
   просто `[...]`.
4. `MarkdownText.kt` использует только `JLatexMathPlugin.create(size)` —
   без `MarkwonInlineParserPlugin`/`inlinesEnabled` (эта связка ненадёжна,
   отключена сознательно).

**Проверка перед коммитом любого нового `math.ru.md`:**
```python
import re
text = open("math.ru.md", encoding="utf-8").read()
spans = re.findall(r'\${1,2}([^$]+)\${1,2}', text)
bad = [s for s in spans if re.search(r'[а-яА-ЯёЁ]', s)]
assert text.count("$") % 2 == 0
assert not bad
assert "\\mathbb" not in text
```
Этот скрипт находил реальные ошибки **дважды** уже после того, как правило
казалось усвоенным (`rf/math.ru.md` с `\mathbb{1}`, `rl/math.ru.md` с
`\mathbb{E}` и кириллицей в `\text{}`) — стоит гонять его по каждому новому
файлу, а не полагаться на память.

## 4. Практика реализации алгоритмов

### 4.1. Численная проверка градиента — обязательна для любого ручного backprop

Перед переносом в Kotlin любой темы с собственной реализацией обратного
распространения — проверять градиент численно в Python:
```python
eps = 1e-4
L_plus = loss_with(param + eps)
L_minus = loss_with(param - eps)
numeric_grad = (L_plus - L_minus) / (2*eps)
# сравнить с analytic_grad — должны совпадать с точностью до 4+ знаков
```
Это находило реальные баги: перепутанный `dL/dp` vs упрощённый `dL/dz` при
сигмоиде (GNN — расхождение было в 4 раза), и подтверждало правильность
сложных случаев (двусторонний градиент в GNN через агрегацию соседей).

### 4.2. Калибровка гиперпараметров — на реальном датасете, не "на глаз"

Диапазоны слайдеров и дефолтные значения подбирались симуляцией на Python
на **тех же данных и seed**, что в итоге попадает в Kotlin — не наугад.
Несколько раз "разумный на вид" диапазон оказывался полностью нерабочим:
- LR: диапазон `0.00001-0.00035` для "сырых" координат (площадь/цена)
  почти везде либо ничего не делал, либо сразу расходился. Решение —
  нормализация признаков внутри алгоритма, после чего разумный диапазон
  (`0.01-1.1`) стал предсказуемым во всём диапазоне.
- RNN: простая (Elman) RNN отлично учится на длине 2-3, но стабильно
  скатывается к случайному угадыванию на длине 6+ **независимо от числа
  эпох** — настоящая проблема затухающего градиента, не баг. Решение —
  сделать длину последовательности главным параметром интерактива, а не
  пытаться "починить" подбором.
- GNN: 1 раунд обмена сообщениями — 79%, 2 раунда — 100%, 3-4 раунда —
  деградация до 50% (over-smoothing). Не монотонная, а "оптимум где-то
  посередине" зависимость — реальная, не искусственная.
- GAN: обучение колеблется, а не монотонно сходится — это подлинное
  свойство состязательного обучения. Не пытаться "стабилизировать" любой
  ценой — вместо этого явно объяснить нестабильность в тексте.

**Практика:** для каждой новой темы с реальным обучением — прогнать Python-
симуляцию по сетке (число слоёв/эпох × learning rate × 3-5 seed), явно
посмотреть на диапазон результатов, и только потом фиксировать дефолты
и границы слайдеров в Kotlin.

### 4.3. Честность про "обучение" — без компромиссов

Для тем, где полноценное обучение неосуществимо в мобильном интерактиве
(Трансформер, Диффузионная модель) — принцип: **либо честно обучаем, либо
явно и прямо говорим, что не обучаем**, без промежуточного варианта
"притвориться, что обучили". При этом там, где можно остаться математически
честным без обучения — оставаться (positional encoding — точная формула
и в реальном трансформере; score-функция для смеси гауссиан в диффузии
вычисляется точно по формуле, без аппроксимации сетью). Явные плашки и
отдельные вопросы в тесте про это — не разовая мера, а обязательная часть
темы, если она принадлежит к этой категории.

### 4.4. Фоновый поток для реального обучения

Любой `Lab.train(...)`, делающий больше, чем тривиальный расчёт (backprop,
Pegasos, Q-learning, message passing) — оборачивается в `Dispatchers.Default`
внутри `LaunchedEffect`, а не считается прямо на главном потоке:
```kotlin
LaunchedEffect(params) {
    delay(100)  // debounce
    result = withContext(Dispatchers.Default) { Lab.train(params) }
}
```
Стандарт применён во всех темах с реальным обучением (кроме LR/LogR/GB/KM —
там расчёт тривиально дёшев).

## 5. Процесс: доставка изменений и синхронизация с репозиторием

- **В зип-архив попадают только реально изменённые в этом ответе файлы**,
  не весь проект — договорённость после случая, когда старая локальная
  копия `AppRoot.kt` (без интеграции чата) была включена в архив "заодно"
  и создала риск регресса.
- Перед отправкой архива — свериться с реальным репозиторием через
  `project_knowledge_search`/GitHub, а не только с локальной копией:
  `project_knowledge_search` отражает **загруженный снэпшот**, который
  может быть старее, чем актуальный репозиторий (так было с `AppRoot.kt`
  и `SplashForeground.kt` — в снэпшоте была версия без интеграции чата).
- Если файл реконструируется по фрагментам поиска (а не редактируется
  точечно) — не гадать неизвестные куски. Если фрагмент поиска
  систематически (2+ раза с разными запросами) обрывается в одном месте —
  это, скорее всего, реальная граница содержимого, а не случайность.

## 6. Справочник: ID тем и где они подключены

Все ID — нижний регистр, используются как `nodeId`/`id` во всех экранах.

**Классические алгоритмы** (`NodeModels.kt`, `defaultNodes()`):
`lr`, `logr`, `knn`, `nb`, `svm`, `dt`, `rf`, `gb`, `km`

**Нейросетевые архитектуры** (`ThirdScreen.kt`, `thirdNodes()`):
`fc`, `ae`, `cnn`, `gan`, `dm`, `gnn`, `rnn`, `tr`, `som`, `rl`

Каждый ID должен быть добавлен в **оба** диспетчера:
- `InteractiveScreen.kt` — ветка `"id" -> XxxInteractive(...)`
- `ResultScreen.kt` — ветка `"id" -> XxxResult(...)`

`AppRoot.kt` и `NodeDetailScreen.kt` — универсальны, новых веток на конкретный
`id` не требуют (кроме случая, когда добавляется целый новый ТИП экрана,
а не тема — как было с `Screen.Chat`).

Ассеты каждой темы — `app/src/main/assets/info/classic/{id}/{general,task,math,impl}.ru.md`.
Код каждой темы — `app/src/main/java/com/eduappml/ui/{id}/{Xxx}Lab.kt`,
`{Xxx}Interactive.kt`, `{Xxx}Result.kt`.
