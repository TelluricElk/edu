# llm-gateway — третий движок чата Edu.AI (llm.armintel.ru)

Маленький HTTP-сервис: приложение спрашивает его, он спрашивает
`llm.armintel.ru` и возвращает ответ в том же формате, в котором отвечает
Edge Function GigaChat. Ничего из уже работающего не трогает — ни Supabase,
ни `voice-relay`, ни `functions/v1/chat`.

```
Android ──http──> llm-gateway :8788/chat ──https──> llm.armintel.ru/api/v1/chat/completions
                       │
                       └── GoTrue /auth/v1/user (проверка токена пользователя)
```

## Зачем прослойка

1. **Токен armintel нельзя класть в APK** — его вытаскивают из пакета за минуту.
   Токен живёт только в `.env` на сервере.
2. **Список моделей меняется.** Он лежит в `.env` и приезжает в приложение
   через `GET /models` — поменять набор моделей можно перезапуском сервиса,
   без пересборки APK.
3. **У armintel свой nginx с таймаутом 60 секунд.** Модель, которая не
   загружена в память, отдаёт `504` с html-страницей. Шлюз превращает это
   в человеческое сообщение вместо «сервер вернул ошибку».

## Установка

```bash
scp -r server/llm-gateway root@157.22.206.53:/root/
ssh root@157.22.206.53
cd /root/llm-gateway && sudo bash deploy.sh
```

Скрипт идемпотентный: повторный запуск обновляет `server.js`, ставит
зависимости и перезапускает сервис, **не трогая заполненный `.env`**. ANON_KEY
он сам достаёт из `~/supabase/docker/.env`; спросит только токен armintel.

В конце он проверяет две вещи: что сервис отвечает на `/health` и что с
сервера реально доходит запрос до `llm.armintel.ru`. Второе может ответить
`504` — это не поломка установки, а незагруженная модель (см. ниже).

Обновление потом — либо повторный `deploy.sh`, либо

```bash
scp server/llm-gateway/server.js root@157.22.206.53:/opt/eduappml-llm-gateway/
ssh root@157.22.206.53 systemctl restart eduappml-llm-gateway
```

## Обновить только список моделей

`apply-models.sh` — отдельный скрипт ровно для этого: правит `ARMINTEL_MODEL`
и `ARMINTEL_MODELS` в уже установленном `.env`, перезапускает сервис и
прогоняет каждую модель живым запросом.

```bash
scp server/llm-gateway/apply-models.sh root@157.22.206.53:/root/
ssh root@157.22.206.53 'bash /root/apply-models.sh'
```

Старый `.env` копируется в `.env.bak.<дата>`; если сервис после правки не
поднялся, скрипт откатывает `.env` сам. Приложение подхватывает новый список
через `GET /models` — **APK пересобирать не нужно**.

## Проверка руками

```bash
curl http://127.0.0.1:8788/health

# С токеном пользователя (SessionManager.getToken() из приложения):
curl -s http://127.0.0.1:8788/chat \
  -H "Authorization: Bearer <supabase access token>" \
  -H "Content-Type: application/json" \
  -d '{"message":"Что такое k-NN?"}'

journalctl -u eduappml-llm-gateway -f
```

Для отладки без приложения можно временно вписать `LLM_GATEWAY_KEY=что-нибудь`
в `.env` и предъявлять его вместо токена. В проде это поле пустое.

## Адреса

| Метод | Адрес | Авторизация | Что делает |
|---|---|---|---|
| GET | `/health` | нет | жив ли сервис, сколько запросов в работе |
| GET | `/models` | да | список моделей для выпадашки в приложении |
| POST | `/chat` | да | вопрос -> ответ |

Префикс `/llm` понимается всегда (`/llm/chat` = `/chat`) — это на случай,
если сервис однажды спрячут за nginx рядом с Supabase.

Тело `POST /chat` намеренно повторяет формат Edge Function GigaChat, поэтому
в приложении переиспользуются те же `ChatHistoryItem` и `ChatResponse`:

```json
{ "message": "...", "history": [{"role":"user","content":"..."}],
  "model": "gemma-3-27b-it",
  "attachments": [{"name":"a.png","mime_type":"image/png","data":"<base64>"}] }
```

Ответ: `{"success":true,"reply":"...","model":"..."}` либо
`{"success":false,"error":"..."}`.

## Какие модели годятся (проверено 17.09.2026)

На сервере около тридцати моделей, но пригодны для чата далеко не все.
Живая проверка каждой:

| Модель | Ответ | Замечание |
|---|---|---|
| `gemma-3-27b-it` | ~1 с | чисто по-русски, стоит по умолчанию |
| `Qwen3.8-Flash-Next` | ~2 с | чисто |
| `FastContext-1.0-4B-SFT` | ~3 с | самая лёгкая |
| `DeepSeek-V4-Flash-Vision-Exp` | ~25 с | понимает картинки, рассуждения в отдельном поле |
| `glm-5.3-Flash`, `cyankiwi/GLM-5.2-AWQ-INT4`, `qwen-3.6-35b-a3b` | 2–3 с | **пишут ход рассуждений прямо в текст ответа** без всяких тегов — в список не берём |
| всё с `owned_by: ollama` (`gpt-oss:*`, `phi4-mini`, `qwen3.5:122b`, `qwen2.5vl:72b`, `hf.co/...`) | `504` | их nginx рвёт запрос на 60-й секунде; ни одна не ответила |
| `*-embed*`, `bge-m3`, `nomic-embed-text` | — | эмбеддинги, текстом не отвечают; шлюз их скрывает |

Отсюда `ARMINTEL_MODELS` в `.env` — четыре проверенные модели. Если Ollama на
той стороне однажды поднимут, модели можно дописать туда же и перезапустить
сервис; приложение подхватит новый список само.

Названия в списке — официальные, как их зовут авторы: **Gemma 3 27B**
(Google), **Qwen3.8 Flash** (Alibaba), **DeepSeek V4 Flash**,
**FastContext 4B**. Приложение показывает их в одном выезжающем списке
рядом с **GigaChat** (Сбер) и **Алисой** (Яндекс) — см.
`ModelMenu` в `ChatScreen.kt`. Те же четыре модели продублированы в
`ArmintelDefaults` на клиенте: список в меню должен быть полным сразу,
до ответа шлюза. **Меняя `ARMINTEL_MODELS`, стоит заглянуть и туда** —
иначе секунду после открытия экрана пользователь видит старые имена.

`STRIP_REASONING=true` вырезает из ответа `<think>…</think>` и harmony-разметку
`<|channel|>analysis…`. Моделям, которые рассуждают без тегов, это не помогает —
их лечение одно: не класть в список.

## Грабли

- **`ARMINTEL_MAX_TOKENS=1024`, а не 512.** Рассуждающая модель успевает
  потратить весь бюджет на размышления и вернуть пустой `content`. При
  пустом ответе и заполненном `reasoning_content` шлюз так и пишет.
- **Запятая разделяет модели в `ARMINTEL_MODELS`** — внутри подписи и
  примечания её быть не должно, иначе список поедет.
- **Токен armintel — обычный JWT без срока в полезной нагрузке**, но отзывается
  на той стороне. Если вдруг посыпались 401 — менять `ARMINTEL_API_KEY`
  и перезапускать сервис.
- **Порт 8788 должен быть открыт** снаружи (deploy.sh открывает его в ufw,
  если ufw включён). Приложение ходит по адресу
  `http://157.22.206.53:8788/` — он прописан в `LlmGatewayClient.BASE_URL`.
- **TLS нет.** Как и у `voice-relay`, трафик идёт по http. Когда перед
  Supabase появится nginx с сертификатом, обе схемы меняются одновременно:
  `https://` в `LlmGatewayClient` и `wss://` в `VoiceConfig`.
